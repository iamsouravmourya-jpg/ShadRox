1. THE TWO ANSWERS, UP FRONT
--------------------------------------------------------------------------------
Q1. Is ShadRox MVP-worthy?
YES — the product itself is MVP-grade. The full loop works and is tested: open
folder → BYOK key → chat → multi-file patch applied atomically → command run →
preview → commit, with per-turn checkpoints, stop-mid-turn, plan/ask refusals
surfaced, and undo. [V] The gates pass right now: `npm run typecheck` exit 0
with 0 errors, and `npm test` = 1771 tests / 28 suites / 0 fail / 0 skipped in
45.9 s. [VR — both run in this session.] That is a stronger position than most
pre-beta tools.

But the MVP as *shipped* has one crash-level bug and one honesty gap:
  • The newest feature (single photo attachment, commit cde73e3) introduced a
    chat-bricking crash on Regenerate and on the one-click "Fix type errors"
    button. One optional-chaining fix. (§3 B1)
  • The landing page still sells ₹399 Starter / ₹999 Pro while the app sells
    ₹699 Starter / ₹1,299 Heavy. [V]

Q2. Is everything on OUR side done for beta testers?
NO. Not because the app is weak — because the scaffolding *around* the app is
missing. Six things stand between this tree and a beta you can invite people
to without burning them:
  B1 the crash, B2 a dead+invisible update channel, B3 zero diagnostics (no
  crash handler, no log file, no error boundary, no telemetry, no DevTools on
  Windows), B4 "by continuing you agree to the beta terms" pointing at terms
  that do not exist, B5 a mandatory Google-only sign-in gate whose config is
  baked at build time, B6 no end-user install guide and no feedback channel a
  non-developer can use.
Estimate to close all six: 4–6 working days. Nothing in this list requires new
product design — it is all shipping-gear work.

Score for the beta question: MVP 8/10, beta-ops 3/10.

3. BLOCKERS — fix before you invite a single tester

B1. Chat dies permanently after "Regenerate" or "Fix type errors".   [V]
--------------------------------------------------------------------------------
src/App.tsx:3327 handleSend(rawText?, historyOverride?, submission?) — the
third parameter is optional. src/App.tsx:3398 reads `submission.attachedImage`
and src/App.tsx:3450 reads it again, both without `?.`, even though every other
use in the same function is guarded (`submission?.envelope` at :3373,
`submission?.attachedFiles` at :3334).
Reachable call sites that omit it:
  src/App.tsx:4942  void handleSend(lastUser.content, history)   → Regenerate
  src/App.tsx:4798  void handleSend(prompt.system + prompt.user) → "Fix type
                    errors" one-click offer
Consequence chain, in order:
  1. src/App.tsx:4933 truncates the messages array BEFORE the throw — the
     user's last assistant reply is already gone.
  2. src/App.tsx:3362 has already set chatDispatchLockRef.current = true.
  3. The lock is cleared only in the finally that starts at src/App.tsx:3955,
     inside a try that begins later at :3796 — never reached.
  4. Every later send sees the lock and queues forever. Chat is dead until the
     app restarts. No error dialog, no log (§B3 means you will never hear about
     it).
Fix: two characters — `submission?.attachedImage` at :3398 and :3450. Then
(1) make the lock release unconditional (wrap the whole body in try/finally),
(2) turn Regenerate into a regression test — this is exactly the class of bug
`strict: false` hides, and 0 of the 1771 tests cover App.tsx:3327 because no
component or hook has any test (47 production modules are referenced by zero
tests [A]).
Effort: 0.5 day including the test.

B2. The update channel is dead AND silent.                 [V] + [VR]
--------------------------------------------------------------------------------
Runtime, checked with curl this session:
  api.github.com/…/releases → v0.0.7 has exactly ONE asset:
      ShadRox-v0.0.7-Setup.exe (137,358,984 bytes, download_count 0)
  v0.0.6 had three: Setup.exe (7 downloads), latest.yml (7), .blockmap (3)
  → https://github.com/…/releases/latest/download/latest.yml
    = 404, redirected to v0.0.7/latest.yml which was never uploaded.
So: 0.0.6 installs poll the feed, get a 404, and 0.0.7 installs get the same.
Nobody ever updates, and nobody knows. Nobody has installed 0.0.7 at all
(download_count 0), which means the build you would be beta-testing has had
zero real-world launches.
Aggravating: the renderer never even asks. electron/preload.cjs:87-88 exposes
checkForUpdates + onUpdaterStatus and src/lib/desktop.ts:715-716 declares both
types — but `grep -rn "checkForUpdates(\|onUpdaterStatus(" src` returns zero
call sites [V]. There is no "Check for updates" button, no badge, no toast;
grep for that copy in src/ finds nothing. Failures are console.warn only
(electron/main.cjs:2846), invisible in a packaged app.
Fix: (1) re-publish v0.0.7 with latest.yml + blockmap; (2) add a release step
that refuses to publish if latest.yml is absent (the file is generated locally
in dist_desktop/latest.yml — it just never got uploaded); (3) subscribe the
renderer and put an "Update available · restart to install" pill in the app;
(4) per security-audit.txt H8, do not leave autoDownload/autoInstallOnAppQuit
on unsigned artifacts.
Effort: 1 day.

B3. Zero diagnostics: no crash handling, no logs, no feedback, no telemetry.
                                                                  [V] [A]
--------------------------------------------------------------------------------
Grep across src/ and electron/ (excluding tests), run by me:
  uncaughtException | unhandledRejection | crashReporter | render-process-gone
  | componentDidCatch | ErrorBoundary → 0 hits.
  electron-log | createWriteStream (log files) → 0 hits.
  mailto: | sendFeedback | reportProblem → 0 hits (the only match is a regex
  inside src/lib/assets.ts:83).
  posthog | sentry | analytics | track() → 0 hits (one test file only).
The only failure surface in the main process is app.whenReady().catch showing a
dialog (electron/main.cjs:2852-2855 [A]). The Windows menu is null
(main.cjs:2825 [A]) and there is no openDevTools path, so a tester cannot even
produce a console screenshot for you.
This is the single most expensive omission in this audit: a beta whose failures
are invisible teaches you nothing, and B1 is proof that at least one invisible
failure exists today.
Fix (all cheap, all one PR):
  process.on('uncaughtException') + ('unhandledRejection') → append to
  %APPDATA%\ShadRox\logs\shadrox.log with rotation;
  window.webContents.on('render-process-gone') → dialog + same log;
  a React ErrorBoundary around the chat/editor panes with "Reload workspace"
  and "Copy diagnostics" actions;
  a "Report a problem" button in Settings that writes a small zip (log tail,
  version, OS, workspace name — no file contents, no keys) and opens a prefilled
  GitHub issue or mailto.
Effort: 1.5–2 days.

B5. Sign-in is mandatory, Google-only, and configured at build time.      [V]
--------------------------------------------------------------------------------
src/App.tsx:5468 — `if (auth.status !== 'signed-in') return <AuthScreen … />`.
Before the gate: no editor, no folder, no file reading, no offline use of the
user's own project. src/lib/authCore.ts:80 hardcodes provider: 'google' — there
is no email/OTP/password path anywhere in the tree.
Two consequences for a beta:
  (a) If the v0.0.7 bundle was built without VITE_SUPABASE_* values, every
      tester hits a wall and the only fix is a rebuild. AuthScreen.tsx:59-66
      does name the missing variables, which is the only reason this is a
      beta-risk and not a hard blocker — but I could NOT verify the shipped
      bundle contains them (dist/ out of scope). Verify one clean-machine
      install before inviting anyone. [V for the code, NOT VERIFIED for the
      artifact]
  (b) Session expiry is only checked at mount (authCore.ts:119), refresh has no
      timeout/abort (authCore.ts:170-180), and on failure the state falls to
      'signed-out' (useAuth.ts:154-167 [A]) → a tester on a train, or behind a
      corporate proxy, is locked out of a local tool by a remote service.
Fix for the beta window: keep Google (fastest to ship) but (1) add an offline
read-only grace state so the workspace/editor still opens without network,
(2) decide now whether email magic links are needed for testers without a
Google account, (3) bake a build-time assertion that fails the desktop build if
Supabase env is missing.
Effort: 0.5 day for (1)+(3).

H4. No crash-safe multi-file transaction.   [A]
    electron/workspace.cjs:929-952 validates then rolls back on partial error,
    but the transaction lives in an in-memory Map; a kill/BSOD mid-loop leaves
    mixed files with no record, and plain bulk save (useWorkspace.ts:1113) does
    not get the rollback that saveFilesAtomic users do. Low probability, high
    pain, and there is no log to reconstruct it (B3).
    Fix: write the staged manifest to disk before committing; on startup, offer
    "finish or discard the interrupted apply".
    Effort: 1 day.

H5. Rewind silently expires on restart — and in a non-git folder that is the
    only undo.   [V]
    electron/machine-delta.cjs:6 LIMITS.records = 8, held in an in-memory Map
    created at :25-26; the limitations string at :106 says so honestly: "Local
    session only: the last 8 snapshots are retained in memory; restarting
    expires rewind." The UI is honest too — src/lib/machine/delta.ts:38 returns
    "Machine snapshot unavailable or expired. No disk rewind is available.", it
    is shown at TimelineSlider.tsx:335 with role="status" and the button is
    disabled at :423. So this is NOT a silent data-loss bug; it is a disclosed
    limitation with two real problems:
      (a) eviction at :146-149 deletes any 'finished' record once you hit 8, so
          ordinary use evicts the state a user wants;
      (b) machine-delta.cjs:135 sets canRestore = false when *any* omission
          exists — one edited PNG or one >2 MB file disables disk rewind for the
          whole turn, silently degrading the whole safety net;
      (c) combined with autoApplyChanges default ON (src/App.tsx:550-556) and no
          git requirement (only an informational note to the model at
          src/lib/agent/tools.ts:505), a tester working in a plain folder that
          Google Drive/OneDrive has no history for has no recovery after restart
          and is never told to use git or to commit.
    Fix: keep a buffer-only restore path for expired machine checkpoints (the
    blobs are persisted — src/lib/history.ts:122-141 — and reload
    works at useWorkspace.ts:315; restoreCheckpoint refuses it at
    useWorkspace.ts:1676-1682 purely on the `machine` flag); degrade per file
    instead of per turn; raise the record cap or spill to disk; and put a
    "this folder is not under git — checkpoints here expire on restart" line in
    the first-run state.
    Effort: 1–2 days.

8. HOW TO RUN THIS BETA SO IT ACTUALLY TEACHES YOU SOMETHING
--------------------------------------------------------------------------------
1. 10 testers, not 50. Two of them on a machine with no dev tools at all. With
   zero telemetry your only signal is conversation, so pick people who will talk.
2. Require a git repo (or a copy) for agent sessions, and say why in the
   invite: post-restart rewind is memory-only (H5).
3. Ship the log file + "copy diagnostics" before you ship the invite link
   (B3), and ask for the log in every report.
4. Tell testers BYOK only, and keep the shared-key section hidden (H1) — the
   honest refusal copy is worse for trust than not offering the box.
5. Fixed feedback ritual: one thread, three questions per tester (what did you
   try, where did you stop, what did you think the app would do). You already
   have the discipline for verbatim short Hinglish prompts; reuse it here
   instead of structured test scripts.
6. Do not publish the pricing page as-is while Starter cannot be bought (H2) —
   the buyer-side math you care about gets judged against the wrong numbers.
